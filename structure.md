# Project Structure

This document describes the standard project layout generated by the scaffold CLI for **Johnny**.

It is written to work across every current preset. Some directories described below are always present, while others appear only when the corresponding module is enabled.

## Design Intent

- Keep backend code inside a standard Python `src` layout.
- Separate delivery concerns such as frontend, infrastructure, and CI from domain code.
- Make it clear where new code should live when developing with an SDD-style workflow.

## Root Layout

Typical project root:

```text
.
|-- README.md
|-- Makefile
|-- structure.md
|-- backend/
|-- frontend/                # optional
|-- infra/                   # optional
`-- .github/                 # optional
```

## Core Files

- `README.md`
  Project overview and quick-start context.
- `structure.md`
  This file. Use it as the structural reference when planning and implementing features.
- `Makefile`
  Common install, test, and local run commands.

## Backend

The backend uses the standard Python package layout:

```text
backend/
|-- requirements/
|-- src/
|   `-- Johnny/
|       |-- __init__.py
|       |-- __main__.py
|       |-- main.py
|       |-- api/                 # if backend_api is enabled
|       |-- application/
|       |-- dispatcher/
|       |-- infrastructure/
|       `-- worker/
`-- tests/
```

### Backend Package Responsibilities

- `backend/src/Johnny/main.py`
  Main backend entrypoint. For API-enabled presets this is the FastAPI app and local run entry.
- `backend/src/Johnny/api/`
  HTTP route definitions and API-facing adapters.
- `backend/src/Johnny/application/`
  Use cases, service contracts, and application-layer interfaces.
- `backend/src/Johnny/dispatcher/`
  Scheduling and dispatch orchestration code.
- `backend/src/Johnny/infrastructure/`
  Logging, database, queue, and other external-system adapters.
- `backend/src/Johnny/worker/`
  Background task workers and task handlers.
- `backend/tests/`
  Backend tests. Add unit and integration tests here rather than inside the package tree.

### Where New Backend Code Should Go

- New API endpoints:
  Add them under `backend/src/Johnny/api/`
- New domain/application contracts:
  Add them under `backend/src/Johnny/application/`
- New database, queue, or third-party adapters:
  Add them under `backend/src/Johnny/infrastructure/`
- New async task handlers or worker entrypoints:
  Add them under `backend/src/Johnny/worker/`
- New scheduling or orchestration logic:
  Add them under `backend/src/Johnny/dispatcher/`

## Optional Module Areas

The sections below apply only when their related module is included in the generated project.

### `backend_api`

Adds the API shell:

```text
backend/src/Johnny/
|-- main.py
`-- api/
    `-- routes/
```

Use this when the project exposes HTTP endpoints.

### `worker_queue`

Adds queue abstractions and worker processing flow:

```text
backend/src/Johnny/
|-- application/interfaces/task_queue.py
|-- infrastructure/queue/
`-- worker/
```

Use this for asynchronous task publishing and background processing.

### `scheduler_dispatcher`

Adds dispatcher logic for due schedules:

```text
backend/src/Johnny/
|-- application/interfaces/schedule_repository.py
`-- dispatcher/handler.py
```

Use this when timed or recurring work needs to enqueue tasks.

### `job_system`

Adds minimal scheduled job models and repository contracts:

```text
backend/src/Johnny/
|-- application/interfaces/job_repository.py
`-- infrastructure/database/models.py
```

Use this when the project needs persistent job definitions or job run tracking.

### `frontend_react`

Adds the frontend application:

```text
frontend/
|-- package.json
|-- index.html
|-- src/
|   |-- App.tsx
|   |-- main.tsx
|   `-- components/
`-- .env.example
```

Keep browser UI, frontend state, and API client code inside `frontend/`.

### `infra_terraform_aws_ecs`

Adds Terraform infrastructure:

```text
infra/
`-- terraform/
    |-- main.tf
    |-- variables.tf
    |-- outputs.tf
    |-- modules/
    `-- environments/
```

This area is responsible for AWS infrastructure such as networking, ECS services, and environment-specific Terraform settings.

### `github_actions`

Adds CI workflow definitions:

```text
.github/
`-- workflows/
```

Keep build, test, and infrastructure validation automation here.

## Preset Reading Guide

You can treat the presets as structural bundles:

- `backend_minimal`
  Core backend package plus API shell.
- `api_service`
  Backend API + Terraform + CI.
- `async_service`
  API + worker/dispatcher/job system + Terraform + CI.
- `fullstack`
  API + frontend + Terraform + CI.
- `mega_bundle`
  Everything currently scaffolded.

## SDD Workflow Guidance

When using this repository structure for SDD-style development:

1. Write the feature intent and target area first.
2. Decide which layer owns the change:
   API, application, infrastructure, worker, dispatcher, frontend, or infra.
3. Add or update tests in `backend/tests/` or frontend test locations as the project evolves.
4. Keep cross-cutting concerns near the edge:
   logging, persistence, queues, deployment, and CI should stay outside application logic where possible.
5. Prefer adding new modules and packages by responsibility rather than by ticket or temporary feature name.
