# Task 3 — Activity detail normalization boundary

Task 3 adds Garmin JSON and original FIT normalizers plus a Garmin adapter method. No activity was fetched, backfilled, analyzed, or published during this task.

JSON laps, typed splits, split summaries, and heart-rate zones retain distinct `source_kind` values. Typed splits and summaries are overlapping/aggregate views, not additional distance or duration. `select_execution_evidence` picks one segment source and one sample source, preferring an integrity-checked FIT recording where available. JSON laps and chart samples cannot claim an exact Workout Step link.

Original FIT is decoded in memory from one bounded ZIP member. The decoder checks archive/member/decompressed limits, rejects traversal names, checks FIT integrity with a fresh stream before decoding, and drops location, identity and device fields. Timer start/stop events mark paused samples; lap timer and elapsed durations remain separate. A repeated `wkt_step_index` receives a repeat occurrence only when a corresponding Workout Step message and a defensible manual or matching timed boundary exist. Automatic distance laps remain unmapped.

The three real-account samples in [Task 1's contract report](2026-10-22-activity-detail-probe.md) initially exposed descriptor keys and factors without establishing a conversion formula. An independent Garmin Connect protocol investigation warns that `factor` must not be applied uniformly ([source](https://github.com/awronski/gconnect/blob/main/GARMIN_CONNECT_PROTOCOL.md#34-units)). The first Task 3 commit therefore retained chart duration, distance and speed as raw values while awaiting FIT comparison.

The user then provided a working local PostgreSQL connection. A read-only query selected three recent owned runs. The existing read-only probe client fetched each chart and original FIT into memory; neither the database nor fixtures received raw activity data. All **4,294 chart points** matched a FIT timestamp within two seconds (1,321 / 1,032 / 1,941 points), and the paired median and 95th-percentile absolute errors were zero for elapsed time, timer time, speed and heart rate. Distance had median error zero and 95th-percentile error 0.0002 m, consistent with numeric precision. These observations establish that the returned values for the observed `second/1000`, `meter/100`, `mps/0.1` and `bpm/1` descriptors are already in seconds, meters, m/s and bpm. The `factor` values must **not** be multiplied or divided into these chart values.

The follow-up `garmin-json-v2` normalizer now emits those physical-unit channels directly and derives pace from positive speed. It continues to require the expected descriptor key, unit and factor; unfamiliar combinations remain missing evidence. Chart coverage remains partial because it is sampled and limited to 2,000 points. FIT still wins whenever both sources are available, while a chart with elapsed-time samples can serve as fallback execution evidence. These three activities had no mid-session pause, so paused chart behavior remains to be verified when a suitable recording exists.

The adapter uses one authenticated client for a bounded detail session, requests chart data with `maxchart=2000, maxpoly=0`, downloads the `ORIGINAL` FIT format, and persists the refreshed session with the existing encrypted credential path after successful work. Its required `provider_activity_id` keeps the Garmin lookup distinct from the local `NormalizedDetails.activity_id` required by the Task 2 repository.
