# Task 4 — Activity detail acquisition and backfill

Task 4 adds durable, owner-scoped batches around the Task 2 snapshot repository and Task 3 Garmin adapter. `activity.detail.fetch.v1` persists a claim before provider I/O, saves normalized snapshots without overwriting older revisions, and records resource failures. `activity.detail.finalize.v1` closes an immutable batch after all items finish or its 120-second deadline expires. Its task payload persists the changed activity IDs and partial flag in the same transaction as batch closure. Task 4 does not start coaching generation; later tasks will consume this finalized manifest.

Summary sync and detail fetches use the same PostgreSQL advisory lock per Garmin connection. Refreshed encrypted credentials commit in a separate transaction before the lock is released, so another worker sees the newest session. A PostgreSQL two-session test verifies both lock serialization and token visibility before the caller's outer transaction commits. SQLite retains the ordinary session write for local tests.

The backfill CLI selects only owned Garmin activities from the previous 28 completed local dates by default, prioritizing the most recent seven dates. `--dry-run` uses a read-only PostgreSQL transaction and reports counts without enqueueing tasks. The live `johnny` database dry-run found 29 eligible activities (6 recent, 23 older). No live detail fetch or backfill enqueue was performed. Actual enqueue and worker processing require `JOHNNY_ACTIVITY_DETAILS_ENABLED=1`; pause and resume preserve completed checkpoints. Rate limits back off, authentication errors block pending work until reauthorization, unsupported resources are not polled again, and recent partial/timed-out data gets at most two delayed rechecks (15 minutes and two hours).

Verification used a freshly migrated, uniquely named disposable PostgreSQL database that was dropped afterward. The integration tests cover overlapping batches, restart/replay, deadlines, owner checks, worker dispatch, retry/reauth, and cross-session locking. The full backend suite passed **818 tests with 0 skipped and 2 existing warnings**. After a final task timestamp correction, focused suites passed 25 tests (one PostgreSQL-only test skipped without the disposable database).
